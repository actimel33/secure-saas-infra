# Архитектура

Схема показывает, **что** построено. Этот документ объясняет, **почему** именно так, и называет альтернативы, которые были отвергнуты.

## Требования

Три требования, из которых следует всё остальное:

- клиенты обращаются к платформе **из интернета**;
- платформа хранит **чувствительные данные клиентов**;
- компания готовится к **аудиту SOC 2**.

Первое требует публичной точки входа. Второе — чтобы эта точка входа была единственной, а данные были отделены от неё несколькими границами. Третье добавляет то, о чём при проектировании часто забывают: каждый контроль должен быть **доказуемым**, то есть оставлять след, который можно показать аудитору.

## Зоны доверия

| Зона | Что внутри | Кто может обращаться | Выход в интернет |
|---|---|---|---|
| Интернет | клиенты, инженеры | — | — |
| Публичная | WAF, балансировщик, NAT-шлюз | интернет по 443 | да |
| Приложение | два инстанса API в разных зонах доступности | только балансировщик | только исходящий, через NAT |
| Данные | PostgreSQL, файловое хранилище | только зона приложения | **нет** |
| Управление | доступ инженеров, логи, ключи, секреты | только по IAM, с MFA | — |

Зоны — это не фигуры на картинке, а отдельные подсети с разными таблицами маршрутизации и разными security group. Обращения идут только в соседнюю зону вниз и только по одному нужному порту: клиент не разговаривает с базой, балансировщик не разговаривает с базой.

**Ключевое свойство зоны данных — отсутствие маршрута `0.0.0.0/0`.** Даже при полной компрометации приложения выгрузить базу напрямую наружу из этой подсети не получится: пакетам некуда идти. Доступ к сервисам AWS из неё идёт через VPC-эндпоинты, не через интернет.

## Потоки данных

| Поток | Протокол и порт | Где заканчивается шифрование |
|---|---|---|
| Клиент → WAF → балансировщик | HTTPS 443, TLS 1.2+ | на балансировщике |
| Балансировщик → API | HTTPS 8443, TLS 1.2+ | на инстансе, сертификат самоподписанный |
| API → PostgreSQL | TLS, 5432 | на базе |
| API → файловое хранилище | HTTPS через VPC-эндпоинт | на стороне сервиса |
| API → интернет (пакеты, обновления) | HTTPS 443 через NAT | только исходящие соединения |
| Инженер → API | Session Manager | канал управления AWS, порт 22 закрыт |

## Принятые решения

### PostgreSQL как управляемый сервис, а не на EC2

**Выбрано:** Amazon RDS.
**Альтернатива:** PostgreSQL на инстансе EC2, как это было сделано на прошлой неделе.

Чем больше берёт на себя управляемый сервис, тем меньше поверхность собственной ответственности. RDS закрывает шифрование диска, автоматические резервные копии, установку исправлений движка и журналирование — всё это контроли, которые аудитор спрашивает отдельно, а в самостоятельной установке каждый из них нужно строить и доказывать руками.

Цена решения: меньше контроля над тонкой настройкой и стоимость выше, чем у инстанса того же размера.

### Один NAT-шлюз вместо шлюза в каждой зоне доступности

**Выбрано:** один шлюз на всю VPC.
**Альтернатива:** по шлюзу в каждой зоне доступности.

Отказоустойчивый вариант стоит вдвое дороже, а NAT — самая дорогая позиция в этой архитектуре (порядок величины — несколько центов в час плюс трафик; точные цифры стоит смотреть в калькуляторе AWS). Для учебного стенда это неоправданно.

Принятый риск: падение зоны доступности, в которой живёт шлюз, оставит без исходящего доступа обе приватные подсети. На работу приложения это влияет ограниченно — входящий трафик идёт через балансировщик и не зависит от NAT, — но обновления и обращения к внешним API прекратятся.

### Роли IAM вместо пользователей с ключами

**Выбрано:** роли, временные учётные данные.
**Альтернатива:** пользователь IAM с постоянной парой ключей для приложения.

Долгоживущий ключ — это то, что утекает: попадает в репозиторий, в историю команд, в образ контейнера. Роль выдаёт временные учётные данные автоматически, и красть, по сути, нечего.

Это решение — прямое следствие инцидента, разобранного в ходе программы: ключ с правами администратора оказался в публичном репозитории. Роль такого класса ошибок не допускает.

### Session Manager вместо bastion-хоста

**Выбрано:** доступ через AWS Systems Manager, порт 22 не открыт нигде.
**Альтернатива:** отдельная машина-бастион с SSH и белым списком адресов.

Бастион нужно обслуживать: обновлять, патчить, раздавать и отзывать ключи, следить за его security group. Session Manager снимает всё это: доступ регулируется политикой IAM, каждая сессия попадает в журнал аудита, а на вопрос «кто заходил на сервер третьего числа» отвечает CloudTrail, а не память команды.

### Секреты в Secrets Manager

**Выбрано:** пароль базы генерируется инфраструктурным кодом и хранится в Secrets Manager.
**Альтернатива:** Parameter Store в виде SecureString.

Оба варианта решают главную задачу — убрать секрет из кода и из пользовательских данных инстанса. Secrets Manager выбран из-за встроенной ротации: для системы, которая готовится к аудиту, «пароль можно поменять автоматически» — отдельный плюс.

Остаточный риск назван честно: сгенерированный пароль попадает в файл состояния Terraform открытым текстом. Поэтому состояние шифруется и лежит в бакете с ограниченным доступом — доступ к состоянию равен доступу к секретам проекта.

### Собственный ключ KMS вместо ключа AWS по умолчанию

**Выбрано:** собственный ключ (customer managed key) с включённой ротацией.
**Альтернатива:** ключи, которые AWS создаёт и обслуживает сам.

Три отличия, которые важны для этого проекта:

**Политика ключа.** У собственного ключа её пишешь ты: какие роли могут шифровать, какие расшифровывать, при каких условиях. У ключа AWS политику можно только посмотреть — она задана сервисом и разрешает использование любым принципалам аккаунта в контексте этого сервиса. Политика ключа работает вторым рубежом рядом с IAM: роль с разрешением на расшифровку ничего не расшифрует, если её нет в политике ключа.

**Жизненный цикл.** Свой ключ можно отключить, запланировать удаление, задать период ротации и повернуть по требованию. Отключение ключа — аварийный рубильник: данные остаются на месте, но прочитать их нельзя, пока ключ не включат обратно. Ключ AWS ротируется принудительно раз в год, и ни отключить, ни удалить его нельзя.

**Область использования.** Ключ AWS работает только внутри своего сервиса и только для принципалов того же аккаунта: зашифрованный им ресурс нельзя передать в другой аккаунт — например, отдать снапшот базы в отдельный аккаунт для резервных копий или аудита. Свой ключ это позволяет.

Что при этом **не** является отличием: использование ключей AWS тоже пишется в CloudTrail. Невидимы только AWS owned keys — ключи, которые живут в аккаунте самого сервиса и применяются по умолчанию в новых сервисах AWS; по ним нет ни политики, ни журнала. Поэтому правильная формулировка такая: собственный ключ гарантирует, что данные не окажутся зашифрованы ключом, который нельзя ни увидеть, ни проверить.

Цена: порядка доллара в месяц за ключ плюс плата за обращения. У ключей AWS ежемесячной платы нет.

### VPC-эндпоинты для доступа к сервисам AWS

**Выбрано:** эндпоинт для файлового хранилища и для каналов управления.
**Альтернатива:** весь трафик к сервисам AWS через NAT.

Эндпоинт оставляет обращения к хранилищу внутри сети AWS: они не выходят в интернет вовсе. Это и дешевле по трафику, и проще объяснить аудитору. Шлюзовой эндпоинт для хранилища бесплатен, интерфейсные тарифицируются по часам, поэтому их набор ограничен необходимым.

### WAF под переключателем

**Выбрано:** WAF описан в коде, но включается переменной.
**Альтернатива:** всегда включён.

Управляемые наборы правил закрывают типовые атаки прикладного уровня без собственной экспертизы, но тарифицируются помесячно. На учебном стенде он включается на время проверки соответствия. **В production он работает постоянно** — это записано здесь явно, чтобы переключатель не выглядел как забытая настройка.

### Шифрование не заканчивается на балансировщике

**Решение:** целевая группа работает по HTTPS на порту 8443, на инстансах поднимается nginx с самоподписанным сертификатом, проверка состояния тоже идёт по HTTPS.

**Альтернатива:** отдавать трафик внутрь по HTTP — так было в первой версии этой инфраструктуры.

Балансировщик сертификат цели не проверяет, о чём AWS пишет прямо: внутри VPC трафик между балансировщиком и целями аутентифицирован на уровне пакетов, подмена и «человек посередине» там невозможны. Отсюда легко сделать неверный вывод, что шифровать участок незачем. Но «нельзя подменить» и «нельзя прочитать» — разные утверждения, а SOC 2 требует шифрования при передаче на всём пути данных, а не только на границе системы. Аудитор смотрит на поток целиком.

Цена решения: сертификат живёт на самом инстансе и обновляется вместе с ним, а не централизованно. Промышленный способ — внутренний удостоверяющий центр (AWS Private CA), но это отдельный платный сервис с ежемесячной платой, несоизмеримой с задачей. Для участка, где вторая сторона сертификат всё равно не проверяет, самоподписанного достаточно: он даёт то, ради чего всё затевалось, — шифрование.

### TLS от клиента: открытый вопрос

Слушатель HTTPS требует сертификата, сертификат — домена, которым владеешь. Собственного домена у проекта нет.

Варианты: зарегистрировать домен и выпустить бесплатный сертификат ACM либо оставить входящий трафик по HTTP и зафиксировать это как незакрытый пробел. Решение принимается при развёртывании и должно быть отражено в разделе ниже — **молча оставить HTTP в проекте про защищённую инфраструктуру нельзя**.

Внутренний, от балансировщика до инстансов, зашифрован всегда. Открытым остаётся только внешний — от клиента до балансировщика.

## Сопоставление с AWS Well-Architected: Security Pillar

Каждый принцип столпа безопасности и решение, которое его реализует:

| Принцип | Как реализован |
|---|---|
| Сильный фундамент идентичности | роли вместо пользователей, права на конкретные ресурсы, никаких долгоживущих ключей |
| Прослеживаемость | CloudTrail во всех регионах с проверкой подписи файлов, flow logs, логи балансировщика, оповещения на критичные события |
| Безопасность на всех уровнях | зоны доверия, security group на каждом переходе, WAF на периметре, шифрование данных |
| Автоматизация лучших практик | вся инфраструктура кодом, сканер конфигурации в CI на каждое изменение |
| Защита данных в покое и в канале | KMS для базы и хранилища, TLS до базы, политика «только TLS» у хранилища |
| Держать людей подальше от данных | доступ к серверам только через Session Manager, реквизиты базы читает приложение, а не человек |
| Готовность к инцидентам | GuardDuty, оповещения, воспроизводимость инфраструктуры из кода |

После развёртывания это же окружение прогоняется через **AWS Well-Architected Tool** (бесплатный, в консоли) по столпу безопасности; отчёт с находками прикладывается к проекту.

## Что сознательно не сделано

| Пробел | Почему так | Что было бы в production |
|---|---|---|
| Один NAT-шлюз | стоимость учебного стенда | шлюз в каждой зоне доступности |
| WAF и AWS Config выключены по умолчанию | тарифицируются постоянно | включены всегда |
| База без Multi-AZ | стоимость | синхронная реплика в другой зоне |
| Восстановление из резервной копии не проверялось | время | регулярные учения по восстановлению |
| Нет собственного домена и сертификата | у проекта нет домена | HTTPS до балансировщика, редирект с 80 |
| Секреты попадают в файл состояния | так устроена генерация паролей в Terraform | генерация вне состояния либо ротация средствами Secrets Manager |
| Нет процесса реагирования на инциденты | за рамками учебной задачи | план, назначенные роли, регулярные тренировки |
